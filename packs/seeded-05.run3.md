## 3. The story
Every source-generator template (object formatter, string-key formatter, enum formatter, union formatter, the generated resolver and the composite resolver) now writes `[global::System.Diagnostics.CodeAnalysis.ExcludeFromCodeCoverage]` on the generated class. The resolver templates also put it on their nested helper classes. Each attribute is wrapped in `#if !NETSTANDARD2_0 && !NETFRAMEWORK`. A one-character fix in TransformUtilities makes the opening brace of a constrained nesting type end with a newline, so the new `#if` lands at the start of a line. About 222 expected-output snapshots were regenerated, a new test class checks the generated text, and the README documents the behaviour.

**Why:** The issue asks for all generated MessagePack code to carry ExcludeFromCodeCoverage so it stops skewing coverage numbers. No setting was added, which the issue says is acceptable.

**Touches beyond the requirement:**
- TransformUtilities.cs line 58 changes the brace emitted after a constrained nesting type from "{" to "{\r\n". This is needed so the preprocessor directive starts a line, but it also changes the layout of existing generated output (the +4/-1 and +5/-1 snapshot shapes).
- Per-target `#if !NETSTANDARD2_0 && !NETFRAMEWORK` guard: a product decision the issue did not ask for.
- README paragraph documenting the behaviour and the guard.

**How sure (the author's own view; it moves nothing):** High that each template now emits the guarded attribute at the intended places; the .tt and .cs pairs match line for line. Medium on the snapshots: only 2 of 222 were visible, and S2 flags 7 distinct shapes, which the brace-newline change plausibly explains. Low confidence that the guard is justified. ExcludeFromCodeCoverageAttribute exists in netstandard2.0 and .NET Framework 4.x, so those consumers get no exclusion and the README states a wrong reason. The new tests check text per generated file, not per type. They do not compile the output and may not exercise the enum or composite templates.
